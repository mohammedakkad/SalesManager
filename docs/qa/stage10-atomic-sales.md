# Stage 10 — atomic Seller commands

Increment 1: creation and its command receipt share one Room withTransaction boundary. DAO-only writes cover sale, invoices, stock quantity/movements, cash balance/movements and receipt. Debt remains derived from sale rows. Missing local cash provisioning fails atomically rather than doing remote I/O in the transaction. Existing PENDING fields are retained; the UI schedules SyncCoordinator only after commit. No outbox or distributed atomicity claim.

Schema24 adds only local operation receipts with a merchant/operation primary key and transaction index. Authentic schema23 migration preservation and injected migration rollback tests pass. Historical schemas1–21 remain unavailable. The schema24 file is Room compiler output.

Before/after creation evidence: the extracted sequential writer failed four real SQLite rollback assertions; withTransaction repairs all four. Seven new command tests plus two migration tests pass alongside the original104 JVM tests. Coverage gates pass. Edit/deletion and backup receipt handling are still being implemented in subsequent increments.

Increment 2: edit uses the same aggregate transaction, validates the loaded sale snapshot, restores only quantities not already returned, replaces invoice lines, deducts the new remaining quantities, and applies net cash differences. The command accepts gross invoice value and subtracts durable refunds to derive net sale/debt. The UI preserves original dates/due-date fields, retains distinct IDs for multiple price lines, and no longer calls independent repositories during edit. Three SQLite fault regressions failed before the edit boundary and now pass; all117 JVM tests and unchanged coverage gates pass.

## Increment 3: deletion and complete lifecycle

Creation, edit and delete now all enter SaleCommands.mutation and the same Room withTransaction boundary. The service imports no network repositories. Both Seller delete screens call the command and have no separate stock restoration or invoice deletion. Deletion reads persisted net amount and returned quantities, restores only the remaining stock, removes return parents/children and invoice lines, deletes the sale, reverses remaining cash, and inserts a local receipt atomically. Stock/cash movement history remains append-only. Deleting a fully returned sale does not refund/restock twice. Missing, physically deleted catalog units are not recreated. Debt is still SUM of unpaid transaction amounts.

The local receipt key is (merchantId, operationId); it records kind, versioned canonical request digest and resulting transaction ID. Repeating an identical command returns its prior result without reapplying effects. Reuse for another payload is rejected. Receipts survive deletion so repeated deletion cannot double-restore stock/cash. The ViewModel retains the create/edit operation ID and date in SavedStateHandle and sets its submitting flag before launching. Invoice IDs remain stable for retries and distinct for multiple price lines.

Room serializes the command's reads/writes. Two last-stock sales cannot both commit. Insufficient stock is rejected rather than clamped, enforcing the existing invoice UI's over-stock rule at the database boundary. Edits/deletes compare the loaded persisted sale (ignoring display names and sync status) before writing; an old command receipt replay does not overwrite a later edit. Cancellation checks and receipt insertion occur before commit; injected cancellation after business writes rolls back every table.

### Explicit financial behavior

Edit input is gross invoice value before recorded refunds; persisted amount/debt and cash use gross minus the existing refund ledger. Replacement quantities cannot be below already-returned quantities. Returned quantities are subtracted once per unit across price lines. Return status is recalculated after replacements; adding a new unreturned quantity to a fully returned invoice makes it partial. This edge case failed before repair (returns-before.log). Missing local cash-box provisioning is an explicit retryable precondition; no remote box is fetched and no guessed initial balance is created inside a sale command. No separate debt ledger was added.

### Schema and backup

Schema24 is additive; no destructive fallback. The authentic23 export migration is checked through Room schema validation, full financial-row preservation and injected migration failure rollback. Historical database versions1–21 remain BLOCKED without authentic schemas. Backup format21 preserves local command receipts, collects its multi-table snapshot in a Room transaction and restores receipts with financial rows atomically. Legacy backups normalize to an empty receipt list and reset that history on restore: duplicate protection cannot extend to operations absent from a historical backup. Receipt rows intentionally have no sale foreign key, so deleting the sale preserves replay protection.

### Stage11 boundary / release status

PENDING business rows retain existing retry behavior; SyncCoordinator is scheduled by the save UI only after the command returns from commit. Best-effort SaleSync deletion runs after commit with captured merchant identity and a current-account check. No Firebase request is made by SaleCommands. Sync fake tests cover scheduling, wrong-account rejection, remote failure and cancellation; they do not contact production.

The receipt table is NOT a transactional outbox: it has no dispatch lifecycle, immutable remote snapshot, lease, acknowledgement or retry schedule. A process exit or network failure can lose remote deletion dispatch. Remote upserts/acknowledgements, stale listeners, account switching during an in-flight request, concurrent legacy non-command writers and restore during sync are not made distributed-atomic by this change. Legacy core repository APIs/remote ingestion and return creation remain outside the three Seller screen command boundaries; this increment does not claim to make every repository operation atomic. Monetary/inventory ordering across devices needs server-enforced revision/idempotency guarantees; no exactly-once or last-write-wins guarantee is claimed. These are Stage11 work, not reasons to omit Stage10 local transactions.
